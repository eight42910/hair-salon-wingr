Performance Audit

美容室ウイング R パフォーマンス分析レポート

本番 URL と現在のローカル実装を突き合わせ、コンソールで懸念されているパフォーマンス低下の要因を実装面・デザイン面から整理したレポートです。

作成日: 2026-06-06 対象: https://hair-salon-wingr.vercel.app/ Next.js 14.2.29 / App Router

概要

PageSpeed Insights API は共有クォータ制限により正式スコアを取得できませんでした。そのため、本レポートでは本番 HTML、レスポンスヘッダー、Chrome ヘッドレス確認、リポジトリ内の実装確認を根拠にしています。

大きな問題は、初期表示に必要な HTML・CSS・JS・フォント・ヒーロー画像の負荷に加えて、静的に見えるセクションまで広く Client Component 化されている点です。視覚面では、デスクトップでも下部予約バーが常時表示され、ヒーローの情報領域を圧迫しています。

本番とローカルの差分に注意: 本番 HTML ではヒーロー画像が /images/salon/salon-bg.jpg ですが、現在の src/app/page.tsx では /images/wingr/hero-storefront-desktop.jpg に変わっています。改善時は、どちらが次回デプロイ対象かを確認してから最適化してください。

レスポンス x-vercel-cache: HIT、content-length: 112866 キャッシュ HIT は良好。ただし HTML 自体はやや大きく、Next Flight の埋め込みも含まれる。
CSS 5 ファイル、合計約 76KB 転送 初期描画に必要な CSS としては許容範囲だが、分割数と未使用スタイルの確認余地あり。
JS 初期 JS 合計約 210KB 転送 サイズだけでなく、静的セクションの hydration と framer-motion の使用範囲がメインスレッド負荷になり得る。
ヒーロー画像 desktop 約 226KB、mobile 約 32KB mobile は適切に 640w が選択されている。desktop はファーストビューの LCP 候補として継続最適化対象。
フォント Noto 系 woff2 が複数ロード 日本語フォントは分割されやすく、体感速度と描画安定性に影響する可能性がある。
Console mobile / desktop ともにエラー未検出 機能エラーよりも、初期読み込み量と hydration 範囲が主な懸念。

改善優先度

Priority 1 ファーストビューを JS 依存から外す

本番 HTML ではヒーロー内テキストのラッパーが SSR 時点で opacity:0 になっており、IntersectionObserver と JS 実行後に表示されます。LCP や FCP の見た目に悪影響が出やすいため、ヒーローだけは初期表示状態を visible にしてください。

  • src/app/page.tsx のヒーロー内 AnimatedSection を外す、または initialVisible のような明示オプションを追加する。
  • 初期表示の h1 / リード文は CSS の軽いフェード程度に留め、非表示開始にしない。
  • prefers-reduced-motion 時は常にアニメーションなしで表示する。

Priority 1 トップのお知らせ取得で本文を含めない

本番 HTML の self.__next_f に最新お知らせの詳細本文 HTML が含まれていました。トップページの一覧表示ではタイトル・日付・カテゴリ・ID だけで足りるため、詳細本文は詳細ページのみで取得するべきです。

  • getNotices 呼び出し時に microCMS の fields を指定する。
  • トップ用に getLatestNoticeSummaries などの小さい取得関数を作る。
  • 一覧カードに本文抜粋が必要な場合も、本文全量ではなく短い要約フィールドを使う。

Priority 1 静的セクションの Client Component 化を減らす

Feature、MenuContent、Staff、Access、NoticeList などが use client と framer-motion に依存しています。表示だけのセクションは Server Component に戻し、必要な操作だけを小さな Client Component に分離してください。

  • 表示専用コンテンツは通常の JSX と CSS transition に寄せる。
  • FAQ、LINE モーダル、モバイルメニュー、地図読み込みなど実インタラクションがある箇所だけ Client Component とする。
  • framer-motion はカルーセルなど効果が明確な部分に限定する。

Priority 2 Google Maps iframe をさらに遅延する

AccessMap の iframe は loading="lazy" ですが、下部セクションの第三者リソースは Lighthouse 上の負荷要因になりやすいです。クリック後読み込み、またはセクション接近後読み込みに変更すると安定します。

  • 初期状態は住所カードと「Googleマップで開く」リンクを表示する。
  • 「地図を表示」ボタン押下、または IntersectionObserver で接近した時だけ iframe を作る。

Priority 2 フォント読み込みを削減する

現在は Noto_Sans_JP、Noto_Serif_JP、Roboto を使っています。日本語サイトではフォントファイルが複数に分割され、表示速度と再描画に影響します。

  • 本文は system font を既定にし、ブランド上必要な見出しだけ日本語フォントを使う。
  • Roboto は英字ラベル用途が主なので、system font で代替できるか確認する。
  • 見出しフォントも使用箇所を限定し、重みを増やさない。

Priority 3 CSS と画像の継続最適化

画像最適化はある程度進んでいますが、desktop ヒーロー画像は LCP 候補です。表示サイズに合わせた素材、AVIF/WebP の採用、品質再調整を継続してください。

  • ヒーローは desktop / mobile で最適な実寸素材を使い分ける。
  • next.config.mjs の minimumCacheTTL は 60 秒なので、安定素材は長めにする余地がある。
  • Tailwind の未使用スタイル、重複 CSS、過剰な影・ぼかしを棚卸しする。

デザイン改善

固定 CTA の表示範囲

MobileReservationBar は名前に反して desktop でも表示されます。デスクトップはヘッダーに電話導線があり、固定バーがヒーロー下部の視認領域を圧迫するため、原則 lg:hidden などで mobile/tablet 限定にしてください。

ヒーロー画像と文字の重なり

店舗外観の実写は信頼感につながっていますが、看板・ドア・店内表示と白文字が重なり、viewport によっては読みづらくなります。テキストの配置、オーバーレイ濃度、背景画像の焦点位置を mobile / desktop で分けると改善できます。

過剰なモーションと装飾

3世代向けの美容室サイトでは、情報への到達速度と安心感が重要です。登場アニメーションは控えめにし、主要 CTA・営業時間・住所・電話番号の視認性を優先してください。

確認方法

  1. npm run lint、npm test、npm run build を実行し、静的チェックとビルドを確認する。
  2. 本番相当ビルドでトップページ HTML サイズ、初期 JS/CSS、ヒーロー画像転送量を再計測する。
  3. mobile 390px / desktop 1440px でスクリーンショットを取り、ヒーローの文字可読性と固定 CTA の表示範囲を確認する。
  4. Chrome DevTools または Lighthouse で LCP、TBT、CLS、ネットワークリクエストを再確認する。
  5. microCMS のトップ一覧取得に本文が含まれていないことを、本番 HTML または Network タブで確認する。
